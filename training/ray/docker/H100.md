## Access

Run client commands from the repository root, with the Chameleon key loaded
in `ssh-agent`:

```bash
ssh -F training/ray/docker/h100-ssh.conf h100-head
ssh -F training/ray/docker/h100-ssh.conf ray-new-3
```

The SSH config enables agent forwarding and reaches private-only nodes
through `ray-worker-2`. Its scoped key record is the ignored file
`training/ray/docker/secrets/h100_known_hosts`.

For the dashboard and MinIO console:

```bash
ssh -F training/ray/docker/h100-ssh.conf -N \
  -L 8266:localhost:8265 -L 9002:localhost:9001 h100-head
```

Open `http://localhost:8266` for Ray and `http://localhost:9002` for MinIO.
Find the head container on the manager with:

```bash
head=$(docker ps -q --filter label=com.docker.swarm.service.name=standalone_ray-head)
docker exec "$head" ray status
```

## Deployment and storage

The new Swarm advertises manager address `192.168.1.185` and uses overlay
pool `10.241.0.0/16`. It is independent of the TACC Swarm. Its image remains
`spectrum-ray:2.54.0-standalone-921290800551`, with Ray 2.54.0 and PyTorch
2.5.1/CUDA 12.4. All six hosts use the same image.

The deployment combines `stack.yaml` and `h100.yaml`. Each `ray.gpu=true`
node runs one `standalone_ray-worker` with one GPU, a 64 GiB `/dev/shm`
tmpfs, and a 16 GiB Ray object store. The head is a separate zero-CPU,
zero-GPU Ray node with a 1 GiB logical memory resource and 1 GiB object store.
There is no four-GPU worker and no separate single-GPU worker service.

Each host stores its source snapshot at `/home/cc/spectrum-usage`, mounted at
`/workspace/spectrum-usage` in containers. Each host keeps its own data and
checkpoint copies; the head and GPU worker share the manager's copy.

The restored source snapshot is local committed revision `5127140`, including
the recovery and training updates that had not yet been pushed. Runtime
inventories and deployment helpers overlay that snapshot. Do not push local
commits or replace them with an older remote revision without checking the
user's intent.

The source store uses the existing `SPECTRUM_*` configuration and Swarm
secrets, populated from local `evaluation/.env`. The new MinIO has newly
generated credentials and volume `standalone_minio-data` on `ray-worker-2`.
Inside jobs, default `AWS_*` variables select MinIO at `http://minio:9000`,
bucket `spectrum-usage`; `spectrum_s3_client()` selects the durable source
bucket `spectrum`.

The completed setup verified matching SHA-256 manifests on all six hosts for
211 processed CSVs (4,131,169,054 bytes) and 510 checkpoint objects
(44,599,296,288 bytes). Each has the location JSON and 35 POWDER
`2400_2600` CSVs. Node-affinity tasks performed CUDA matrix multiplication
and PyTorch shared-memory allocation on every GPU and verified a roughly
1 MiB MinIO object written on `ray-new-3` and read on all six workers.
The result is `runs/infra/h100-rebuild-acceptance-20261107.json` on the manager.

Redeploy on the manager when an image or service configuration change is
intended:

```bash
source /home/cc/spectrum-storage.sh
export RAY_IMAGE=spectrum-ray:2.54.0-standalone-921290800551
docker stack deploy --resolve-image never \
  -c /home/cc/spectrum-usage/training/ray/docker/stack.yaml \
  -c /home/cc/spectrum-usage/training/ray/docker/h100.yaml standalone
```

For routine asset refreshes from the workstation:

```bash

  bash training/ray/scripts/sync-cluster-data.sh
RAY_INVENTORY=training/ray/docker/standalone-nodes.sh \
  bash training/ray/scripts/sync-cluster-data.sh --checkpoints
```

## Recovery records

Before leaving the orphaned old Swarm, we preserved the stopped workers'
writable-layer files using same-filesystem hard links. These root-only
directories survive removal of the old containers without duplicating their
file contents:

- `ray-worker-1`: `/home/cc/ray-recovery/c210d0c58f50faf143b3530fb74ea30223f342f5944243c3a1f887297a1371f4/`
- `ray-worker-2`: `/home/cc/ray-recovery/d3d47d6c86a53a069fa412804a0c689463526e5ba826e393e3c6fd5aca288ffc/`

Each contains `rootfs-upper/`, a file/inode manifest, and container metadata.
We verified the saved inodes after both workers left the old Swarm. These
files are not automatically mounted into the replacement worker containers.
The hosts' existing repository data and checkpoints stayed in place.

The durable MinIO backup prefix is `s3://spectrum/oct2026-minio-backup-newcluster/`.
It contains 4,087 objects, 551,205,275 bytes, with latest object modification
at **2026-11-06 14:48:46 UTC**. Restore job
`h100-minio-restore-fast-20261107` copies those keys into the new MinIO. It
replaced the initial slower job `h100-minio-restore-20261107` and skips objects
already copied with the expected size. The final record is
`runs/infra/minio-restoration-20261107.json` in the manager's repository. This
recovers backed-up tuning state, not the lost Ray head's live job processes.
The restore succeeded for all 4,087 objects, with no size mismatches; ten
JSON objects also matched the backup's SHA-256 content checks.
Training jobs must be submitted again or resumed through their own runner;
cluster setup does not restart them automatically.

## Lease-aware operation

The two older instances outlive the four new ones by 28 hours 20 minutes.
Swarm node labels record each deadline as `lease.end`. Before
**2026-11-09 13:40 UTC**, finish or checkpoint work on `ray-new-*`, then
drain those nodes. Draining a node terminates its worker container, so do it
after preserving any required work, not as a way to checkpoint it.

The manager, MinIO, and the two old GPUs can then continue until
**2026-11-10 18:00 UTC**. Keep durable backups current and move the head or
finish work before that final deadline as well. No automatic shutdown or
training-job restart has been scheduled.
